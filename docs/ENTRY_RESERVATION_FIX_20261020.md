# 최초 매수 준비 중 예산 초기화 경쟁 조건 수정

2026-10-20 22:45 KST 신호는 LONG 64.5%, 2주 수량 계산까지 기록됐지만, 로컬 주문 이벤트와 연쇄 주문 의도는 없었다. 남은 book은 예산과 사이클이 비어 있고 같은 09:45 NY 봉에서 평탄화 처리된 상태였다. 당시 스레드 순서는 기록되지 않았으나, 수량 계산과 주문 실행 사이에 빈 원장 대사를 실행하면 같은 현상을 격리 환경에서 재현할 수 있었다.

## 수정

- `RelayBook.begin()`이 예산과 함께 현재 book 인스턴스의 최초 매수 준비 소유자를 원자적으로 저장한다. 이미 시작한 사이클 예산을 두 번째 begin이 교체하지 못한다.
- 빈 원장 대사와 예산 예약은 같은 book 잠금을 사용한다. 현재 봉에서 해당 인스턴스의 최초 매수가 준비 중이면 보유·주문이 아직 없어도 사이클 완료로 처리하지 않는다.
- INITIAL 주문 의도 저장과 동시에 준비 상태를 해제한다. 그 이후에는 기존 영속 주문 원장이 보호한다.
- 주문 전 실패, 15분 평가 예외/종료 시 준비 상태를 해제하고 위험 감시를 깨운다. 새 봉으로 넘어가거나 프로세스 재시작으로 소유자가 달라진 미제출 준비는 비어 있는 원장이 확인되면 정리할 수 있다. 미확정 제출·부분 체결·미해결 주문은 이 절차로 지우지 않는다.
- 준비 해제 중 저장 오류가 나더라도 진입 mutex는 finally에서 해제한다. 저장 장애의 기존 fail-closed 처리는 유지한다.
- 실제 매수 함수가 확인 실패로 돌아오면 브리핑에 `BUY_EXECUTION_NOT_CONFIRMED`를 표시한다. 모델 승인만으로 주문 가능 상태를 계속 표시하지 않는다.

49%·49%, 연쇄 1회, -1% 연쇄 조건, 최초/연쇄 추적 발동, -0.3% 추적, -2% 손절, 원장·계좌 READY·미체결 처리 조건은 변경하지 않았다.

## 쉐도우 지연 관련

기존 worker는 7,921.8ms 입력 지연으로 격리 종료됐고, 종료 시 8개 전략 전체의 미해결 포지션은 0이었다. Windows PROCESS_MODE_BACKGROUND_BEGIN은 CPU 외에 I/O·메모리까지 제한하므로, 실시간 감사 로그 기록과 공유 메모리 소비를 늦출 수 있다. 해당 모드 진입을 제거했다. launcher와 guard의 below-normal CPU 우선순위는 유지한다. 2초 입력 freshness, WebSocket 출처 검사, overflow/gap 격리 규칙은 완화하지 않았다.

백그라운드 I/O 제한이 관측 지연의 유일한 원인이라고 확정하지 않는다. 실제 장중 지속 수신 검증은 다음 Runner/worker 실행 후 필요하다.
